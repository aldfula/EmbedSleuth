# v0.2.0 검증 기록 — 2026-11-27

구현과 오프라인·설치 검증, 실제 Pi의 절전 해제·5회 센서 수집·원래 절전 복원을 완료했다. v0.2.0 공개 배포를 준비한다. 새 기능의 전체 SSH 메모리·실제 모델 행동과 오류 주입은 실물 미검증이다. 아래 결과를 v0.1.0의 실물 인수와 합쳐 새 기능 전체가 실물 검증됐다고 해석하지 않는다.

## 자동 회귀

최종 전체 회귀 **888 passed in 54.47s**, 경고 오류 처리. 실물 인수 클라이언트와 완료 보고서 보존·복구 우선순위 두 회귀를 포함한다. 로컬 소켓/자식 프로세스를 허용한 환경에서 가짜 장치로 실행했으며 실제 Pi·외부 모델·운영 설정은 사용하지 않았다. 직전 885개 전체 회귀와 등록 선언 보호를 포함한 19개 집중 검사도 통과했다.

새 테스트는 기존 설정·다른 MCP/훅·README 보존, 반복 적용과 dry-run, malformed/중복 형식·링크·수정 스킬 거부, 실패 rollback, 새 외부 등록과 v0.1.0 원본 이전을 포함한다. 센서에서는 signed 변환과 16가지 범위 조합, 절전/활성, 지원하지 않는 설정, SLEEP 외 클록 비트 보존, 승인 없음/만료/변조/소진, durable intent 이후 만료, 오류·정상 복원·불확실한 IO·복원 실패·타인 설정 변화, 중복/재시작 캐시와 격리를 확인한다.

실제 MCP 런타임과 Pre/Post/Stop을 묶어 계획·로컬 승인·샘플·보고서를 시험했다. 외부 작업이 없는 sampling_planned 상태의 턴 종료는 허용하고, 미완료 원격 작업은 대기 예외로 숨기지 않는다. 로컬 승인 저장소 열기는 다른 실행을 자동 복구하지 않는다. 파이프 승인은 거부한다. 스킬 quick_validate도 통과했다. 이 시험은 실제 LLM의 라우팅이나 자연어 보고 품질을 평가하지 않는다.

`scripts/run_sampling_acceptance.py`는 운영자 본인 TTY에서 새로운 생산 STDIO MCP의 두 센서 도구를 확인하고, 현재 주소/충돌 배제 확인·식별·계획·생산 로컬 승인 명령·환경 갱신·수집·최종 보고서 조회를 한 번 수행한다. 승인을 생성하거나 I2C를 직접 조작하는 대체 경로는 없다. 가짜 장치 7개 조건에서 정상·거절·승인 누락·기한 경과·이전 서버 거절·비TTY·false 등록 선언을 확인했다. 실제 Pi의 별도 실행은 아래 실물 인수에 기록한다.

제한 환경에서는 MCP 로컬 통신 검사가 정지해 해당 실행을 중단했고, 이후 로컬 소켓/자식 프로세스를 허용한 환경에서 180초 상한으로 전체 검증했다. 실제 Pi·외부 모델·운영 설정을 사용하지 않았다.

## 빌드와 설치

wheel과 sdist를 만들고 `twine check --strict`를 통과했다. wheel의 코드/리소스 25개와 sdist의 같은 파일을 현재 소스와 바이트 단위로 비교했다. 메타데이터 이름·버전·UTF-8 README를 확인했고 경로 이탈·링크·비공개 설정 포함이 없음을 검사했다. README 문서 링크는 PyPI에서도 사용할 절대 GitHub 링크로 바꿨다.

1. 공개 PyPI v0.1.0을 새 임시 pipx 환경에 설치하고 실제 v0.1.0 setup으로 작업 폴더와 등록을 생성했다.
2. 같은 pipx 환경을 위 v0.2.0 wheel로 업그레이드했다. 가상환경 활성화 없이 앱 4개를 실행했다.
3. v0.1.0 작업 폴더에 --in-place를 적용해 스킬을 이전했다. 원래 README·등록·구 INSTALLATION.json이 유지됐고 재적용은 변경 0개였다. 백업은 프로젝트 밖이었다.
4. 다른 MCP 서버가 있는 별도 기존 프로젝트에 새 외부 등록을 만들며 적용했다. 기존 README·서버·공유 쓰기 가능한 일반 .gitignore를 보존했고, 생성 MCP는 pipx Python을 사용했다.
5. pip check와 설치본의 실제 setup·스킬·STDIO MCP 11개 스키마/프로필·훅 3개를 확인했다. 등록 대상 0개·장치 검사 0회·모델 0턴·신뢰 자동 부여 없음이다.

사용자 전역 pipx·셸 설정·운영 등록·기존 진단 저장소를 변경하지 않았다. 새 후보를 PyPI나 GitHub Release로 업로드하지 않았다.

## 실물 인수

운영자가 본인 PC 터미널에서 생산 STDIO MCP 인수 클라이언트를 실행했다. 기존 target_id·SSH 신뢰·공유 증거 저장소를 유지하고 현재 주소 0x68·다른 I2C 사용자 중지와 기존 로컬 충돌 배제 선언을 확인했다. 첫 실행 run-da33e4b6591b4506a5ea4eb174c2e6f8은 `approve`만 입력해 정확한 계획 문자열 확인에 실패했다. 수집 호출 0회·깨우기 없음·partial 보고서·닫힌 MCP로 종료됐다. 식별 읽기는 승인 전 절차로 수행됐으며 수집 승인으로 오해하지 않는다.

### 이전 MCP 프로세스와 보고서 조회

운영자 출력은 complete였으나, 기존 호스트에 남아 있던 이전 버전 MCP의 get_report가 새 프로필을 재평가해 partial로 보고서를 덮어쓰는 문제를 발견했다. 원시 증거·승인·복원과 감사는 변경되지 않았다. 변경된 보고서 스냅샷을 비공개 로컬에 보존한 뒤 최신 생산 STDIO MCP의 finalize_report/get_report로 기존 증거만 재정리했다. 최종 complete·원시 증거 동일·미완료 감사 없음·원격 호출 0회를 대조했다.

v0.2.0 get_report는 복구를 먼저 확인한 뒤 reported 상태이고 증거가 같은 완료 스냅샷을 재판정·재저장하지 않게 보완했다. 완료 후 새 원격 불확실성이 발견되면 복구 판정이 우선하며 이전 complete를 그대로 내보내지 않는다. 두 조건을 회귀에 추가했다. 이미 로드된 v0.1.0 프로세스에는 패치가 소급되지 않으므로 업그레이드 후 기존 MCP를 종료·재연결해야 한다.

## 남은 검증과 배포 경계

- 새 변경 절차의 실물 취소/복원 불확실성·전체 SSH 메모리는 미검증이다. 오프라인 오류·취소·복원 시험과 v0.1.0의 실물 결과를 구분하고, 이전 64MiB 전체 과금 메모리 결과를 새 기능 보장으로 재사용하지 않는다.
- 새 스킬 흐름의 실제 모델 행동과 승인 대기/재개는 별도 범위 승인 후 평가한다. 이번 실물 실행에는 LLM 호출이 없다.
- 이미 활성 상태에서 설정 쓰기를 생략하는 경로는 오프라인 검증이며 이번 실물은 원래 절전 상태였다.
- PC Python 3.11·다른 OS·다른 pipx/uv 백엔드는 이번 실행 검증에 포함하지 않는다.
- 기존 Trusted Publisher의 같은 워크플로/환경으로 별도 v0.2.0 매니페스트·Release를 검증한 뒤 게시한다. v0.1.0 파일/태그/매니페스트는 유지한다. 최종 배포 해시와 공개 설치 결과는 게시 후 별도 절에 추가한다.
