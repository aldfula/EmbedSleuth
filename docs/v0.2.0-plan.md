# v0.2.0 확장 계획

상태: 구현·로컬 설치 검증과 실제 Pi의 절전 해제·5회 수집·원래 절전 복원 통과. v0.2.0 GitHub Release/PyPI 게시와 공개 pipx 새 설치까지 통과했다. 전체 SSH 메모리·실제 모델의 새 흐름은 별도 미검증이다. [검증 기록](v0.2.0-verification.md)을 따른다.

## 범위

기존 Linux 작업 폴더에 EmbedSleuth 연결 자료를 병합하는 `embedsleuth-setup --in-place`와 MPU6050의 짧은 가속도·자이로·온도 점검을 추가한다. 기본 passive/read_only 동작과 기존 등록·증거·격리를 유지한다. 기존 시스템 변경 금지 정책의 예외는 로컬 운영자가 승인한 일회성 센서 점검뿐이다.

## 기존 폴더 적용

기존 README와 소스는 수정하지 않는다. 다른 MCP 서버·훅·설정을 보존하며 EmbedSleuth 소유 항목만 추가한다. 기존 항목의 의미가 충돌하거나 스킬이 수정되어 있으면 중단한다. TOML은 원문에 전용 테이블을 추가하고 파싱으로 확인하며, JSON 훅은 다른 이벤트·그룹을 보존한다. 설정 diff의 원문에는 비밀이 있을 수 있으므로 파일 이름과 변경 종류만 출력한다. 적용 전 백업·중단 표시를 저장하고, 실패 시 자신이 쓴 파일만 되돌린다. 강제 덮어쓰기와 호스트 신뢰 자동 부여는 제공하지 않는다. 미완료 적용 표시는 자동으로 무시하지 않는다.

## 센서 점검과 승인

명시적인 `sensor_check` 모드에서만 준비한다. `prepare_sensor_sampling`은 식별이 확인된 등록 대상에 대해 로컬 계획을 만든다. 계획은 대상 등록과 SSH 신뢰 digest, run, 부트, 어댑터, 주소, 정책, 만료에 결합한다. MCP는 승인 불리언·토큰·레지스터·명령을 받지 않는다. 로컬 운영자 명령은 계획을 보여주고 실제 터미널 확인을 받은 뒤 승인 기록을 저장한다. 승인 권한은 MCP에 노출하지 않는다.

`sample_sensor_data`는 승인과 최신 선행 조건을 다시 확인하고 승인 사용을 전송 전에 영속 저장한다. 원격 검사기는 식별과 설정을 확인한 뒤 필요하면 PWR_MGMT_1의 SLEEP 비트만 해제한다. 리셋·범위 변경·DMP·FIFO·드라이버 우회는 수행하지 않는다. 고정된 14바이트 burst를 짧게 반복해 원시값과 실제 범위에 따른 단위를 기록하고, 변경했다면 원래 PWR_MGMT_1을 복원하고 읽어 확인한다. 이미 활성 상태이면 설정 쓰기를 생략한다. 다른 설정·부트·대상 변화나 전송 완료 불명확 상태에서는 추가 동작을 멈춘다.

복원은 finally 경로와 제한된 원격 실행 시간으로 시도한다. 전원 차단·SIGKILL·커널 I/O 정지·통신 단절에서 복원을 보장한다고 주장하지 않는다. 복원이 확인되지 않거나 원격 완료가 불명확하면 영속 격리하고 자동 재시도하지 않는다. 승인 범위는 읽기의 부수 효과와 일시적 전력·센서 상태 변화도 포함한다. 다른 I2C 프로그램 중지는 기존 로컬 운영 선언을 계속 요구한다.

반복 값은 정지 상태나 낮은 샘플 속도에서도 나타날 수 있다. 고정값·포화·온도 범위는 경고/unknown으로 보고하며 고장·정품·측정 정확도를 확정하지 않는다. 독립적인 새 센서 업데이트나 정밀 주기 계측을 보장하지 않는다. 제조사 register map의 4.17–4.19(측정·변환), 4.28–4.29(전원), 4.4–4.5(범위)와 product specification의 기동·환경 조건을 근거로 한다. 프로필의 기존 문서 SHA-256을 유지하고 추가 검토 범위를 따로 표시한다.

## 검증·배포 순서

1. 설정 병합: 기존 파일 보존·다른 서버/훅·반복 적용·충돌·링크·잘못된 형식·실패 복구·dry-run.
2. 결정적 센서 디코딩, 허용 레지스터와 변경 비트, sleep/awake/거부 조건, 정상·오류·취소·복원 실패.
3. 코어의 승인 없는 실행 거부·위조 인자 거부·만료/소진·변경된 대상·중복 작업·격리·보고서와 훅.
4. 전체 오프라인 회귀와 새 wheel/pipx 설치 인수. 실제 모델·Pi 검사와 구분한다.
5. 실제 Pi에서 현재 주소·다른 프로그램 중지·구체적인 변경 계획 승인을 새로 확인하고 깨우기·데이터·복원을 검증한다. 실물 미검증이면 명시한다.
6. 검증 결과 검토 후 v0.2.0 태그/Release/PyPI 게시를 진행한다. 기존 v0.1.0 배포 파일과 매니페스트는 교체하지 않는다.
