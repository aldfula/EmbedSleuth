# 실행 중 취소 한 건의 재부팅 후 복구 계획

상태: 2026-11-26 사용자가 이번 취소 건의 복구와 메모리 검사를 별도로 승인했고, 적용·보고서 대조를 완료했다. 부팅 설정 승인을 격리 해제 승인으로 재사용하지 않았다.

## 이번 대상과 근거

- 대상은 기존 등록 ID·키·신뢰 파일·공유 저장소를 그대로 사용하는 Pi 한 대다.
- 범위는 run-c9db8ec922444ce58b5907d5eedfdfc6의 취소 격리 한 건이다. 이 실행은 passive inspect_target 한 번만 시작했고 센서 전송은 없었다. before/after가 닫혔고 pending=null·취소 표시가 남아 있다.
- 기존 부트 관측과 현재 부트 ID가 다르고, 기존 등록·호스트 신뢰에 결합한 SSH 연결에서 새 부트를 독립 확인했다. 이전 부트의 프로세스는 새 부트에 남을 수 없다. 다른 불명확한 대상 실행은 없었다.
- 관리자 준비 결과 파일과 실제 Pi의 재확인 모두 백업·변경 파일 해시 일치와 memory controller 활성화를 확인했다. 메모리 측정의 준비 완료이며 64MiB 예산의 통과는 아니다.

## 승인 후 수행할 변경

1. [로컬 복구 명령](../scripts/recover_passive_cancel.py)을 --confirm-local-recovery로 실행한다. root·sudo는 사용하지 않는다. 현재 부트·검증된 호스트 지문·등록 digest·다른 활성/미확정 실행 부재를 다시 확인한다.
2. 기존 대상 잠금·모든 관련 실행 잠금·격리 잠금을 획득한다. 상태가 달라졌거나 잠겨 있으면 중단한다. 다른 원인의 격리, 센서 읽기, 열려 있는 원격 작업에는 이 절차를 사용하지 않는다.
3. 취소 실행 디렉터리에 소유자 전용 passive-reboot-resolution.json을 원자적으로 기록·fsync한다. 이전/현재 부트·호스트 지문·등록 digest·기존 감사/evidence digest·원래 격리 사유·운영자 확인을 보존한다.
4. 이 기록이 영속화된 다음 기존 격리 파일 한 개를 제거하고 디렉터리를 fsync한다. 중간 실패는 격리를 유지하며 자동 재시도하지 않는다. 임의 파일 삭제·저장소 교체·새 target_id는 사용하지 않는다.
5. 원래 실행·보고서·센서 증거·감사 내용은 유지한다. 원래 보고서는 interrupted/unknown이며 정상으로 바뀌지 않는다. 기존 실행을 재개하거나 재전송하지 않는다. 새 코드의 시작 시 복구는 기록의 해시 결합을 검증해 과거 취소만 확인 처리한다. 기록이나 원격 감사가 달라지면 시작/dispatch를 차단한다. 예전 조회기가 덧붙인 정확한 무전송 recovery(operation_ids=[], error_code=remote_state_unknown) 접미부만 최대 64개까지 허용한다. 원래 감사 prefix digest와 before/after·evidence 결합은 유지하며 다른 접미부는 거부한다.

## 이후 검증

- **새 생산 STDIO MCP 연결**에서 새 passive 검사로 현재 보드·환경을 확인한다. 이전 코드를 메모리에 로드한 MCP 서버는 이 확인 기록을 이해하지 못하므로 재연결이 필요하다. 승인 전의 기존 호스트 호출을 그대로 유지한 채 격리 파일만 삭제하는 방식은 쓰지 않는다. 예전 서버를 계속 쓰면 안전 측면에서 다시 차단될 수 있다.
- 사용자가 이번 재부팅 후에도 유지하겠다고 확인한 0x68·다른 I2C 작업 배제 선언을 식별 한 실행에만 반영한다. 실행 전후 원래 등록 파일을 보존·복원하고 동일 대상·공유 저장소를 유지한다. 새 서버는 등록을 새로 읽으며 진행 중 등록을 바꾸지 않는다.
- 조건이 충족되면 WHO_AM_I를 한 번 읽고 보고서를 마친다. 오류·불명확한 완료 뒤 자동 재시도는 하지 않는다. 0x69는 읽지 않는다.
- [커널 메모리 관측기](../evals/diagnose-mpu6050/cgroup_observer.py)와 [인수 실행기](../scripts/run_cgroup_acceptance.py)는 SSH 서비스와 user.slice의 memory.peak를 함께 읽는다. 계측 프로세스·기존 세션·다른 작업도 포함하는 생성 이후 상한이다. 과거 peak를 빼서 이번 사용량이라고 계산하지 않는다. 카운터 초기화·프로세스 이동·서비스 재시작·추가 sudo는 하지 않는다.
- 각 검사기의 /proc/self/cgroup 관측과 sshd 그룹이 집계 범위 안인지 검사한다. 계층·inode·부트·카운터·관측이 확인되지 않으면 unknown이다. memory.peak는 과금 메모리이고 RSS 합계와 다르므로 두 지표를 바꾸어 쓰지 않는다. 기존 엄격한 추가 peak RSS 목표를 이 승인으로 수정하지 않는다.

## 구현·검증

복구는 로컬 운영 명령이며 공개 MCP 도구는 계속 9개다. 소스는 [storage.py](../src/embedsleuth/storage.py)에 있고 [복구 안전성 시험](../tests/test_passive_recovery.py)은 승인·부트·등록 불일치, 센서/추가 작업, 다른 불명확 실행, 저장 실패, 기록 변경, 읽기 전용 접근을 거부하는지 검증한다. [계측 판정 시험](../tests/test_cgroup_acceptance.py)은 그룹 누락·교체·카운터 초기화·RSS 혼동을 다룬다. 최신 전체 709개가 48.88초에 통과했다.

실제 승인 적용 뒤 passive 검사와 0x68 식별 1회까지 완료했다. 과금 메모리 상한은 각각 약 37.7MiB·38.0MiB로 64MiB 아래였다. 마지막의 예전 호스트 조회기가 격리를 재생성해 호환성 회귀 4개를 추가하고, 유휴 상태의 해당 MCP 프로세스만 정상 종료했다. 이미 승인된 같은 취소 건을 다시 확인 처리하고 새 생산 MCP에서 저장된 보고서만 검증했다. 장치 검사는 반복하지 않았다. 현재 대화의 이전 MCP transport는 닫혔으므로 일반 호스트 사용에는 MCP 재연결이 필요하다.
